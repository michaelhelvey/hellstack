**Goal**: Create a pull request to `main` from the current branch with a title and description that
accurately describe the changes being proposed.

Additional (optional) information from user about the pull request: $ARGUMENTS

## Steps

1. Understand the changes being made in the pull request. Sources of information include (in order
   of importance):
   - The output of `git diff origin/main...HEAD` (or similar command) to understand the code changes
     being proposed.
   - The branch name, if it follows a descriptive convention.
   - The commit messages in the branch, if they are descriptive and follow a convention.
   - Your overall understanding of the project, when you explore it to understand the context for
     the changes.
2. Write a detailed pull request description. See below for guidance on writing good pull request
   descriptions.
3. Use the `gh` CLI tool to create a pull request to main from the current branch with the title and
   description you have written.

## Pull Request Description Guidance

_Overall guidance: Remember that your target audience is other developers reviewing this pull
request. You are not here to "sell" the pull request, convince anyone of anything, complement the
author of the code, or anything other than to enable the reviewers to understand and review the pull
request. You are an engineer writing for other engineers on the same team. Your tone should be
technical, concise, and straightforward._

**Title**:

Prefer a ticket-prefixed title when a ticket number can be inferred from the branch name:

- Format: `[AA-000]: <summary>`
- Example: branch `ct-123-add-new-feature` -> `[CT-123]: <summary>`

If no ticket can be inferred (for example branch format `feature/<slug>`), use this fallback format:

- `<summary>`

The summary should be concise and accurate commit message-style description of the changes being
proposed, ideally less than 72 characters.

**Body**:

The pull request body must follow the following format:

- **AI Callout**: Start the body with the following italicized text, with no heading.

  > _Note: the following PR description was generated by <model-name>. If it sucks let Michael know
  > so he can update his agent skills._

  For example, if you are Claude Sonnet 4, then `<model-name>` should be `Claude Sonnet 4`.

- **Summary**: A high-level summary of the changes being proposed. This should be a few sentences
  worth of information that provides the reader an high-level understanding of what and why the
  changes are being proposed. Include a JIRA link only if a ticket number can be inferred from the
  branch name. If no ticket is inferred, explicitly state that no ticket was found.

- **Reviewers Guide**: A detailed guide to reviewers of where to look to understand the changes
  introduced by this pull request. Do NOT walk through the diff. Reviewers can read the diff for
  themselves. Instead, group the changes into logical sections, and within each section, write
  concise, bullet-point explanations of the changes. Be specific: reference specific files,
  functions, or lines of code where relevant.

- **Testing and/or Demo**: A description of how to test or view the changes being proposed in
  action. For example, if the pull request introduces a new page on a website, include instructions
  for how to navigate to that page and test out the changes. If the pull request is to a library,
  include examples of what code that consumes that library should look like because of the changes
  in the pull request.

## Output Guidance

- All text must be written using ASD-STE100 Simplified Technical English. It should be simple,
  straightforward, and jargon free. Say exactly what you mean, in the active voice, without abstract
  bullshit.
- Keep it short, even if the PR is big. If I want to get an AI agent to walk me through the PR in a
  verbose way, I have plenty installed on my computer already, I don't need the PR description for
  that. I need to be able to see what this PR does and why in less than 30 seconds.
